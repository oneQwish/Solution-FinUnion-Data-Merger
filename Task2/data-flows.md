# Потоки данных: промежуточное состояние через 3 месяца

Диаграмма: diagrams/data-flow-diagram.drawio (PNG — diagrams/data-flow-diagram.png). Внешние сущности — клиенты, регулятор, владельцы справочников и пользователи данных. Потоки между операционными системами, MDM и DWH идут через Integration Layer: ESB FinUnion для синхронных вызовов, Kafka для событий, CDC для съёма изменений из баз данных без доработки систем, Schema Registry для контрактов данных: несовместимое изменение схемы источника останавливается на входе в Kafka и не ломает потребителей. Напрямую идут выгрузки из DWH в BI и регулятору, сбор метаданных в DataHub и выгрузки систем RetailBank в RB DWH, которые остаются как в As-Is.

Согласованность по операциям:

- Выдача глобального ID в MDM требует строгой согласованности: у клиента не может быть двух ID. При недоступности MDM новый клиент создаётся в CRM без глобального ID и получает его после восстановления, через ручной разбор при подозрении на дубль.
- Раздача золотой записи, контактов и справочников в системы-потребители допускает отставание в пределах SLA потока: устаревший на минуты контакт не останавливает обслуживание.

## CRUD-матрица промежуточного состояния

C — Create, R — Read, U — Update, D — Delete (мягкое), V — Validate, E — Enrich, A — Aggregate. Мастер справочников — MDM, коды RetailBank сопоставлены с кодами FinUnion. Системы RetailBank до вывода хранят локальные копии справочников: новые продукты в них не заводятся, изменение тарифа или отделения повторяется вслед за решением владельца в MDM (U*) и сверяется потоком 18. Системы RetailBank не дорабатываются, поэтому из MDM в них ничего не передаётся: соответствие идентификаторов RetailBank глобальным хранится в MDM.
