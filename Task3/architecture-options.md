# Сравнение архитектурных вариантов

| Вариант | Плюсы | Минусы | Когда подходит | Применимость к FinUnion + RetailBank |
|---|---|---|---|---|
| DWH на PostgreSQL | Строгая схема и транзакционность; точная сверка с учётными системами; зрелая технология, у FinUnion уже есть DWH | Дорого хранить и обрабатывать большие объёмы истории и событий; ограниченно масштабируется под тяжёлые запросы | Регламентированная отчётность, умеренные объёмы, строгие требования к точности | Подходит для регуляторной и управленческой отчётности; не подходит для полной истории операций обоих банков |
| Data Lakehouse | Дешёвое хранение больших объёмов; табличный доступ через SQL; история версий таблиц | Нет ограничений целостности, как в реляционной БД: сверка и контроль качества строятся отдельно; требует новой экспертизы | Большие исторические и событийные данные, аналитика рисков и антифрода | Подходит для истории операций и событий; основа уже есть — Data Lake FinUnion, сейчас без потребителей и каталога |
| Data Mesh | Владение данными у доменов; масштабирование аналитики по бизнес-направлениям | Требует зрелых доменных команд и общих стандартов; при слиянии домены двух банков ещё не объединены | Зрелые организации с устоявшимися доменами | Полный Data Mesh в год слияния преждевременен; применимы его элементы — data-продукты с владельцами |

Выбран гибридный подход:

- DWH на PostgreSQL — для регламентированной и управленческой отчётности;
- Data Lakehouse на основе Data Lake FinUnion — для больших исторических и событийных данных;
- элементы Data Mesh — data-продукты по доменам BIAN с владельцами из правил владения данными.

Обоснование: регуляторной отчётности нужны точность и сверка с учётными системами, которые даёт DWH; полная история операций двух банков дешевле и удобнее в Lakehouse; владение данными по доменам закрывает отсутствие владельцев в As-Is, не требуя перестройки организации в год слияния.
