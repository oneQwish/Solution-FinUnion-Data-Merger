# Пайплайны данных

| Пайплайн | Источник | Приёмник | Тип | Инструменты |
|---|---|---|---|---|
| Простой пайплайн DWH на 3 месяца: договоры и счета обоих банков | FU Core, RB Core | DWH на PostgreSQL | ELT: CDC в staging, затем core и витрины | Debezium, Kafka, Kafka Connect, PostgreSQL, dbt, Airflow |
| Клиентские данные | FU CRM, RB CRM | MDM, затем DWH (измерение клиента) | Near real-time, затем ELT | Debezium, Kafka, MDM, dbt |
| Справочные данные | MDM | FU Core, FU Cards, FU Loans, DWH | Событийная репликация | Kafka, Kafka Connect; в DWH — dbt |
| Финансовые данные | Core, Cards, Loans | DWH | ELT | Debezium, Kafka, dbt, Airflow |
| Регуляторная отчётность | DWH | Формы отчётности регулятора | Batch: формирование форм из витрин DWH по графику отчётности | Airflow, dbt |
| Метаданные и lineage | MDM, DWH, Lakehouse, Kafka | DataHub | Batch по расписанию | DataHub, Airflow |

Простой пайплайн на 3 месяца: изменения договоров и счетов из FU Core и RB Core снимаются Debezium и пишутся в Kafka; Kafka Connect загружает их в staging-таблицы PostgreSQL как есть. Staging — изолированный сырой слой: доступ к нему только у инженеров данных, а ПДн в core не переносятся, клиент там представлен глобальным ID. dbt по расписанию Airflow переносит данные в слой core: приводит данные обоих банков к единой модели, заменяет идентификаторы клиентов на глобальные из MDM, сопоставляет коды продуктов RetailBank с кодами FinUnion и хранит историю изменений. Строки без глобального ID клиента или без сопоставленного кода продукта не отбрасываются: они уходят в карантин с причиной и разбираются стюардами Data Office. Повторная загрузка не создаёт дублей: запись в core ищется по бизнес-ключу — ID в системе-источнике и банк. События CDC могут прийти не по порядку, поэтому изменение с более ранней позицией в журнале транзакций не перезаписывает более позднее. Событие удаления из CDC закрывает запись в core (дата окончания и признак удаления), а не стирает её. Витрины строятся из core. Один запуск обрабатывает один день, витрины за этот день перезаписываются целиком, поэтому пересчёт прошлых дней после смены правил сопоставления не создаёт дублей. У задач Airflow три повтора с задержкой и SLA по срокам из карточек качества и потоков (данные для отчётности — до 06:00, витрины BI — до 08:00); при сбое или просрочке алерт уходит дежурному инженеру данных и владельцу данных.

ELT выбран, хотя DWH на PostgreSQL. Объём умеренный: полная история вынесена в Lakehouse. Трансформации — SQL-модели dbt внутри хранилища, отдельный сервер трансформации с лицензиями не нужен. Сырые данные в staging позволяют пересчитать core и витрины, когда меняются правила сопоставления кодов RetailBank с кодами FinUnion, а при слиянии они будут меняться. Цена — трансформации нагружают PostgreSQL, поэтому пересчёты идут по расписанию до окна BI (до 08:00), а при росте объёма MPP-СУБД остаётся в зоне Assess технологического радара.

## Обработка больших исторических и событийных данных

| Поле | История карточных операций обоих банков | Архив RetailBank после вывода систем |
|---|---|---|
| Источник данных | FU Cards, RB Cards, исторические выгрузки в Data Lake FinUnion и RB DWH | Финальные выгрузки RB Core, RB CRM, RB Cards, RB Loans; документы |
| Характер данных | Исторические и событийные | Архивные, полуструктурированные |
| Целевое хранилище | Data Lakehouse (таблицы Iceberg) | Объектное хранилище; востребованная часть — таблицы Lakehouse |
| Способ обработки | История до контрольной точки T0 — разовой batch-загрузкой на Apache Spark порциями по месяцам, проблемную порцию можно повторить отдельно; изменения после T0 — streaming из Kafka в Bronze-слой через Kafka Connect (Airflow потоковую обработку не выполняет) | Batch ELT при выводе каждой системы |
| Потребители | Риск-менеджмент, антифрод через Trino | Data Office, ответы на запросы регулятора, аудит |
