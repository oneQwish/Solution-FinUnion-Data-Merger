# DWH и Data Lakehouse

## Сравнение для FinUnion + RetailBank

| Критерий | DWH на PostgreSQL | Data Lakehouse |
|---|---|---|
| Контроль целостности и сверка с Core | Встроенный: строгая схема, транзакции, ограничения БД (ключи, уникальность) | Внешний: Iceberg даёт транзакционную запись, но не ограничения целостности; сверка и проверки качества строятся отдельно |
| Объём данных | Умеренный | Большой: полная история операций двух банков |
| Стоимость хранения | Выше | Ниже: файлы в объектном хранилище |
| Что есть в As-Is | DWH у обоих банков | Data Lake только у FinUnion, без каталога и потребителей |
| Основные потребители | Финансовый департамент, регулятор, BI | Риск-менеджмент, антифрод, аналитики |

Lakehouse нужен по трём признакам больших данных: объём — полная история операций двух банков; скорость — непрерывные события карточных операций и каналов; разнообразие — документы, сканы и полуструктурированные выгрузки RetailBank. Регламентированной отчётности ни один из этих признаков не нужен, поэтому она остаётся в DWH.

## Подход по этапам

- Через 3 месяца: DWH FinUnion на PostgreSQL получает данные обоих банков через CDC и Kafka и строит минимальный набор витрин для BI по правилам FinUnion. Lakehouse не используется.
- Через 12 месяцев: DWH остаётся на PostgreSQL для регламентированной и управленческой отчётности. Data Lake FinUnion развивается в Lakehouse: в него загружается история операций обоих банков и события, а данные выведенных систем RetailBank лежат в архиве в объектном хранилище.

## Роль Apache Iceberg, каталога и Trino

- Apache Iceberg — табличный формат поверх файлов в объектном хранилище: схема, транзакционная запись, версии таблиц. Превращает файлы Data Lake FinUnion в таблицы.
- Каталог Iceberg (REST-каталог или Hive Metastore) хранит ссылку на текущий снимок каждой таблицы. Новая версия публикуется атомарным переключением этой ссылки, поэтому потребитель видит либо старую, либо новую таблицу целиком. Это технический каталог таблиц, он не заменяет DataHub: DataHub ведёт описание данных, владельцев и lineage.
- Trino — SQL-движок: получает из каталога текущий снимок и выполняет запросы к таблицам Iceberg и, при необходимости, к DWH одним запросом. Даёт аналитикам доступ к Lakehouse без переноса данных в DWH.

## Что где хранится

| Данные | Где | Почему |
|---|---|---|
| Витрины управленческой отчётности | DWH | Нужны единые определения метрик и быстрый доступ BI |
| Данные для регуляторной отчётности | DWH | Требуется сверка с учётными системами до копейки и воспроизводимость: данные фиксируются снимком на дату закрытия периода, формы пересобираются из снимка с теми же цифрами, каждый показатель прослеживается до операций в Core через lineage в DataHub |
| Измерения клиентов и справочников с историей изменений | DWH | Основа для всех витрин |
| Полная история транзакций и карточных операций обоих банков | Lakehouse | Большой объём, нужна для риск-моделей и антифрода, а не для отчётности |
| События карточных операций и каналов | Lakehouse | Поток событий большого объёма |
| Данные выведенных систем RetailBank | Архив в объектном хранилище, востребованная часть — таблицы Lakehouse | Хранение по срокам закона без поддержки старых систем |

## Слои Lakehouse

| Слой | Данные | Доступ |
|---|---|---|
| Bronze | Исходные выгрузки и CDC-события обоих банков, финальные выгрузки систем RetailBank | Инженеры данных |
| Silver | Данные с глобальными ID клиентов из MDM и кодами продуктов FinUnion, без технических дублей | Аналитики по ролям; ПДн заменены глобальным ID |
| Gold | Наборы для риск-моделей, антифрода и data-продуктов | Потребители по ролевой модели |

## Ограничения подхода

- Два хранилища: одна и та же операция может быть в DWH (агрегатом) и в Lakehouse (детально); расхождения ловятся сверкой при загрузке. Чтобы не было двух версий одного показателя, показатели управленческой и регламентированной отчётности считаются только в витринах DWH; Gold-слой Lakehouse такие показатели не публикует.
- Lakehouse требует новой экспертизы команды: Iceberg и Trino в As-Is не используются.
- PostgreSQL ограничен по объёму и тяжёлым запросам; при росте отчётности потребуется пересмотр выбора.
- Не проработаны промышленные параметры Lakehouse: партиционирование, размер файлов и их объединение, срок хранения снимков, отказоустойчивость каталога. Они определяются на этапе 5 плана миграции и влияют на стоимость и производительность.
