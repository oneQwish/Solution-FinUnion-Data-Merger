# Целевая архитектура данных через 12 месяцев

Диаграмма: diagrams/target-data-architecture.drawio (PNG — diagrams/target-data-architecture.png).

К 12 месяцам системы RetailBank выведены из эксплуатации, их данные перенесены в системы FinUnion или в архив. Операционная и аналитическая нагрузки разделены: банковские системы обслуживают клиентов, отчётность и анализ выполняются в DWH и Lakehouse.

| Компонент | Роль | Обоснование |
|---|---|---|
| Operational Systems: FU Core, FU CRM, FU Cards, FU Loans | Ведение счетов, договоров, операций, платежей, карт, кредитов, обращений | Целевыми выбраны системы FinUnion; финансовые данные остаются в профильных банковских системах |
| MDM Customer Hub | Золотые записи клиентов, справочники продуктов, тарифов, отделений и сегментов | Устраняет дубли клиентов и расхождение справочников двух банков |
| Integration Layer: ESB FinUnion | Синхронный обмен между системами | Существующая шина FinUnion; на неё переведены потоки, которые в RetailBank были point-to-point |
| Kafka и Schema Registry | Событийные потоки: изменения клиентов, справочников, финансовых данных; контракты данных | Один механизм доставки изменений в MDM, DWH и Lakehouse; изменения сегмента и других атрибутов попадают в историю DWH по событию. Kafka Connect загружает события в staging DWH и Bronze-слой Lakehouse |
| CDC | Съём изменений из баз операционных систем | Не требует доработки систем и не создаёт аналитической нагрузки на них |
| DWH на PostgreSQL | Регламентированная и управленческая отчётность, витрины BI | Существующее хранилище FinUnion, достраивается, а не строится заново; объём регламентированной отчётности умеренный, большие объёмы вынесены в Lakehouse |
| Data Lakehouse: объектное хранилище, Apache Iceberg, каталог Iceberg, Trino | Большие исторические и событийные данные | Строится на основе Data Lake FinUnion: у него появляются табличная структура, потребители и каталог |
| Архив RetailBank в объектном хранилище | Данные выведенных систем RetailBank | Хранение данных по срокам 402-ФЗ и 115-ФЗ без поддержки старых систем. Архив неизменяем: перезапись и удаление запрещены до конца срока хранения; по истечении срока данные удаляются или обезличиваются. Сроки хранения по категориям данных ведёт Data Office |
| Airflow | Оркестрация batch-пайплайнов | Расписание, зависимости и повторные запуски загрузок. По DAG на каждый data-продукт и на загрузку каждого источника; зависимости между ними — через готовность опубликованного набора данных. Выбран вместо Dagster и Prefect: для всех компонентов платформы (PostgreSQL, Kafka, Spark, dbt, DataHub) у него есть готовые операторы, и специалистов по нему проще найти. Потоковую обработку не выполняет, данные через Airflow не проходят: он запускает загрузки, Spark и модели dbt |
| dbt | Трансформации внутри DWH и Lakehouse | Модели на SQL с тестами качества; расчёт метрик по единым правилам FinUnion. Формулы метрик утверждает Финансовый департамент, ошибки в показателях разбирает Data Office |
| BI | Дашборды и управленческая отчётность | Существующий BI FinUnion, переведён на витрины объединённого DWH; критичные метрики берёт из витрин и не пересчитывает |
| DQ-контур | Правила качества, их прогон, история метрик, витрина качества, карантин | Правила версионируются отдельно от кода трансформаций и публикуются в DataHub; прогоняются тестами dbt в пайплайнах Airflow; результаты копятся в DWH; при нарушении порога алерт уходит владельцу данных; карантин разбирают стюарды Data Office. Пороги — в карточках качества задания 2 |
| DataHub | Каталог данных, lineage, владельцы | Трассируемость происхождения данных и владение данными, которых в As-Is нет ни у одного банка |
